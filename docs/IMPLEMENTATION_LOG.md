# Implementation log

## المرحلة الأولى — 2026-09-09

- استُخدم Laravel الموجود (13.31.0)، وثُبت Boost 2.8 وBreeze 2.4.2 وSpatie Permission 8.3.
- أُعدت المصادقة والتحقق من البريد واستعادة كلمة المرور والتسجيل بإنشاء شركة ومالك داخل معاملة.
- أُنشئت موديلات المجال العشرة وحقول User وعلاقاتها وfactories وseeders.
- أُضيف عزل البيانات وقيود العلاقات بين الشركات وسياسات كل موديل والأدوار الستة.
- أُضيفت واجهة Blade/Tailwind/Alpine مشتركة، ترجمة AR/EN وRTL/LTR، قوائم حسب الدور، استعراض وتفاصيل السجلات والتقارير وتنزيل المستندات.
- أُصلح إعداد MySQL المحلي الذي كان يستخدم MyISAM باعتماد InnoDB في اتصال المشروع.
- نُفذت migrations وseed على rentflow؛ الاختبارات تستخدم rentflow_testing.
- البريد التجريبي يكتب في log؛ يلزم SMTP للإرسال الفعلي.
- النطاق التالي: شاشات وإجراءات CRUD، دورة الصيانة، التحصيل، التسجيل الآلي للتدقيق، واشتراكات SaaS.

## التحقق

تغطي اختبارات Pest مصادقة Breeze، التسجيل الآمن، الأدوار الستة، العربية والإنجليزية، السياسات والاستعلامات، الوصول بين الشركات، تخصيص المستأجر والصيانة، القيود الفريدة والمفاتيح المركبة والمستندات وseed المتكرر.

- Pest على MySQL: **57 اختبارًا ناجحًا، 289 assertion**.
- Playwright على Chrome: **6 اختبارات ناجحة**؛ Desktop/Tablet/Mobile × EN/AR، تسجيل الدخول وتبديل اللغة والتنقل وترقيم الجداول ونافذة الحساب؛ دون أخطاء JavaScript أو امتداد أفقي للصفحة.
- نجح npm run build وcomposer validate وPint وgit diff --check وتجميع Blade وroute cache.
- أكد Composer أن Laravel 13.31.0 أحدث إصدار مستقر متاح أثناء التنفيذ.
- روجعت لقطات الواجهة، وأُصلح امتداد أفقي سببه عنصر قارئ شاشة داخل الجدول على الهاتف.
- لا توجد أخطاء معروفة تمنع تشغيل المرحلة الأولى. الإرسال الفعلي للبريد يتطلب إعداد SMTP.

## المرحلة الثانية — إدارة المباني والوحدات والمستأجرين — 2026-09-09

- أضيفت عمليات CRUD كاملة للمباني والوحدات والمستأجرين، باستخدام Controllers متخصصة وForm Requests مع إعادة استخدام Policies وCompanyScope الموجودة.
- المباني: بحث بالاسم والرمز والعنوان، تصفية بالحالة والمدينة، ترقيم الصفحات، تفاصيل المبنى وإحصاءات الوحدات وجدولها.
- الوحدات: تصفية بالمبنى والنوع والحالة، بطاقات إجمالي/مؤجرة/شاغرة/صيانة، نماذج المواصفات والإيجار، وتفرّد الرقم داخل المبنى.
- المستأجرون: البحث وبيانات التواصل والطوارئ، العقد والوحدة الحاليان، وسجلات العقود والدفعات والصيانة والمستندات المرتبطة. الأقسام تخضع لصلاحية المستخدم لكل مورد.
- الشركة تُستنتج من الحساب؛ الوحدة تستنتج شركتها من المبنى المصرّح به. مدير النظام يختار شركة عند إنشاء المبنى أو المستأجر، ولا يمكن نقل ملكية سجل موجود إلى شركة أخرى عبر النموذج.
- الحذف داخل معاملة مع قفل السجل والتحقق من ارتباطاته: يمنع حذف المبنى ذي الوحدات والمستأجر ذي العقد النشط، ويحافظ أيضًا على التاريخ المالي والمستندات. تظهر رسالة مترجمة عند الرفض.
- SaveUnit يضبط اتساق المبنى والطابق والحالة داخل معاملة؛ تُمنع إعادة نقل الوحدات المرتبطة بسجلات أو جعل وحدة ذات عقد نشط شاغرة. لا يمكن تقليل طوابق مبنى دون معالجة الوحدات في الطوابق الأعلى.
- الواجهة: رؤوس صفحات ومسارات تنقل، قائمة مستخدم، بطاقات وجداول وحقول مشتركة، ترقيم صفحات وفلاتر، حالات فارغة، تنبيهات نجاح وأخطاء، ونافذة تأكيد حذف. استُكمل RTL للقوائم المنسدلة والنماذج والتنقل.
- لم تُضف تبعيات أو migrations أو ملفات توثيق جديدة. أُعيد استخدام قاعدة البيانات والمصادقة من المرحلة الأولى.

### تحقق المرحلة الثانية

- **8 اختبارات متصفح ناجحة**: ست حالات EN/AR على Desktop/Tablet/Mobile، وحالتا CRUD كاملتان تشملان الإنشاء والتعديل والفلاتر والحذف الآمن وقائمة المستخدم ونافذة التأكيد.
- اختُبر منع الوصول والتعديل والحذف لشركة أخرى بتغيير ID في الروابط، ورفض المبنى الأجنبي في نموذج الوحدة، ومنع الكتابة للأدوار المقيدة.
- نجح npm run build وPint وتجميع Blade وgit diff --check، وروجعت لقطات النماذج والقوائم على سطح المكتب والهاتف.
- بيانات اختبارات المتصفح مؤقتة وأزيلت بعد الاختبار؛ بيانات Demo الأصلية باقية.
- لا توجد عوائق معروفة لهذه المرحلة. عمليات العقود والتحصيل والصيانة التشغيلية وإدارة المستندات خارج نطاق هذه المرحلة.

## المرحلة الثالثة — 2026-09-09

- أُضيف CRUD للعقود، وشاشات التحصيل والمتأخرات وتسجيل الدفع، ودورة طلبات الصيانة، باستخدام Controllers وForm Requests وPolicies مع الخدمات الثلاث: LeaseContractService وRentPaymentService وMaintenanceWorkflowService.
- العقد يبدأ مسودة أو نشطًا. التفعيل يقفل الوحدة داخل معاملة، يمنع التداخل مع عقد نشط، ويغيّر حالتها إلى occupied ويولّد الجدول مرة واحدة. تُقفل الأطراف والتواريخ والمبالغ بعد التفعيل لحفظ السجل المالي؛ يبقى تعديل رقم العقد وإنهاؤه متاحًا، والحذف للمسودات غير المرتبطة فقط.
- الفوترة: دفعة إيجار كاملة لكل شهر تقويمي يشمله العقد، دون تجزئة الإيجار. يوم 31 يُضبط لآخر يوم في الأشهر القصيرة، وتُحصر أول وآخر دفعة ضمن مدة العقد. القيد الفريد للعقد وتاريخ الاستحقاق يمنع التكرار.
- الإنهاء يلغي الدفعات المستقبلية غير المسددة مع إبقاء المدفوعات السابقة والأرصدة المستحقة. انتهاء المدة أو الإنهاء يحرّر الوحدة عند عدم وجود عقد نشط آخر، ويحافظ على حالة maintenance إذا كانت مضبوطة مسبقًا.
- تسجيل الدفع يقفل الدفعة، يقبل pending/overdue فقط، ويسجّل paid_at وpayment_method دون السماح بتغيير المبلغ أو تكرار التحصيل.
- الصيانة تطبق الانتقالات المحددة فقط، وتتطلب عقدًا ساريًا لإنشاء الطلب. التعيين لمدير الشركة/مدير العقار أو مدير النظام، ولموظف صيانة نشط من الشركة نفسها. الموظف يتابع طلباته المسندة فقط، ويستطيع بدء العمل وإكماله وإضافة ملاحظات داخلية.
- أُضيف MaintenanceActivity وعلاقته المقيدة بالشركة لتاريخ الحالات والملاحظات. المستأجر لا يرى الملاحظات في الاستعلامات أو الواجهات. تُسجّل أحداث الإنشاء والتعيين وتغيير الحالة والإكمال في AuditLog داخل المعاملة نفسها.
- تنبيهات Laravel عبر database داخل التطبيق: استحقاق خلال ثلاثة أيام، تأخير، تسجيل دفعة، طلب جديد للإدارة، تعيين للموظف، وتحديث حالة للمستأجر. التذكيرات لا تتكرر، ومركز التنبيهات يتيح القراءة لصاحبها فقط، مع ترجمة الرسالة حسب اللغة الحالية.
- الواجهات تستخدم المكونات المشتركة، ملخصات مالية وفلاتر وجداول متجاوبة، نافذة تأكيد الدفع، تسلسلًا زمنيًا، وترجمة AR/EN ودعم RTL. لم تتغير التبعيات أو ملفات التوثيق الأخرى.
- نُفذت الترحيلات الإضافية دون إعادة بناء بيانات Demo. سُجّلت مهمتا leases:expire يوميًا 00:05 وpayments:update-overdue يوميًا 08:00 بتوقيت التطبيق، مع withoutOverlapping. نُفّذ الأمران يدويًا للتحقق.
- التشغيل الآلي: استخدم php artisan schedule:work محليًا، أو شغّل php artisan schedule:run كل دقيقة على الخادم. التنبيهات الحالية داخل التطبيق ولا تحتاج SMTP أو عامل Queue.
